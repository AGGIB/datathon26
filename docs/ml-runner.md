# Локальный запуск полного pipeline для оценки

`ml.eval_runner` запускает только локальный Python на той же физической машине. Он не запускает облачные вычисления, не устанавливает зависимости, не скачивает модели и не заменяет отсутствующий анализ mock-ответом. Файлы видео не просматриваются средствами разработки; тесты используют только искусственные модули и байтовые заглушки, не являющиеся медиа.

## Python-интерфейс

```python
from pathlib import Path
from ml.evaluation_labels import load_labels
from ml.eval_runner import run_pipeline
from ml.eval import score

labels = load_labels(Path('open_labels.xlsx'))
predictions = run_pipeline(
    labels,
    videos_dir=Path('data/videos'),
    pipeline='ml.pipeline:analyze',
    time_budget_sec=240,
    timeout_sec=300,
    output_dir=Path('artifacts/pipeline-evaluation'),
)
report = score(labels, predictions)
```

Сигнатура:

```python
run_pipeline(labels, videos_dir, pipeline='ml.pipeline:analyze',
             time_budget_sec=240, timeout_sec=300, output_dir=None) -> list[dict]
```

При `output_dir=None` используется `artifacts/eval-runner` относительно корня репозитория, независимо от текущей рабочей папки. Явно переданные относительные пути разрешаются относительно текущей папки вызывающего процесса. Для результатов выбирайте локальную папку, исключённую из Git, например `artifacts/...`. Дополнительной публичной CLI-команды здесь нет: родительская CLI может импортировать и вызвать эту функцию. `_worker` — внутренний протокол, не пользовательский интерфейс.

- `labels` — список записей с `video`, `positive`, `timestamp`, полученный штатным загрузчиком оценки. Возвращается одна prediction на каждую запись, в исходном порядке, включая ошибки файлов и анализа.
- Сопоставление использует `audit(..., use_ffprobe=False)` и общий helper `ml.evaluation_labels.video_key`: без декодирования кадров и без `ffprobe`, но с локальным хешированием сопоставленных файлов. Канонический ключ следует штатному `normalize_video_name`, включая регистр, stem имени и варианты латинской `X` / кириллической `Х`. Исходные идентификаторы сначала валидируются; коллизии канонических ключей в одном источнике отклоняются. Runner сохраняет исходный `video` из labels и открывает буквальный путь из `matched_paths`, не строит имя файла из нормализованного ключа.
- `pipeline` — только `module:function`: имена ASCII-идентификаторов, модуль может быть составным через точки, функция — одно имя. Импорт выполняется через `importlib` исключительно в дочернем процессе. Выражения Python, пути к скриптам, `eval`, `exec`, shell-команды не поддерживаются.
- Вызывается `function(local_absolute_video_path, on_progress=None, time_budget_sec=...)`.
- Оба бюджета — числа `int`/`float`, конечные, строго больше нуля и не больше 300; `bool` и строки запрещены. Мягкий бюджет передаётся pipeline, жёсткий независимо контролируется runner. Можно уменьшить только `timeout_sec`: даже если мягкий бюджет больше, worker будет принудительно остановлен по жёсткому пределу.
- Пути к видео и результатам — локальная файловая система: URL, UNC/device-пути и сетевые диски Windows отклоняются. Используйте доверенные локальные папки без ссылок на удалённые хранилища.

## Predictions и артефакты

Успешный ответ pipeline должен быть словарём с `verdict` (`violation` / `no_violation`) и списком `violations`. Отсутствующий `status` трактуется как `done`. Непустой список должен соответствовать `violation`, пустой — `no_violation`. Проверяются объекты событий, тип события при его наличии, конечные неотрицательные числовые времена и порядок `t_start <= t_peak/timecode_sec <= t_end` для переданных границ. Это проверка контракта оценки, не полная Pydantic-валидация evidence из backend.

Успешная prediction содержит:

- `video` — точный идентификатор из входной записи, а не из ответа модели;
- `status: done`, `verdict`, `violations` — фактический результат анализа;
- `elapsed_sec` — измеренное монотонными часами полное время данной попытки: подготовка запроса, запуск интерпретатора, импорт/холодный старт модели, анализ, обмен JSON и завершение/очистка процесса.

В каждом событии сохраняются только явно разрешённые поля оценки: `type`, `timecode_sec`, `t_start`, `t_peak`, `t_end`, если они присутствуют. `evidence_frames`, base64, описания, observations и любые другие поля/вложенные объекты удаляются **до записи worker response**, а при чтении ответа родитель повторно применяет тот же allowlist перед checkpoint. Полный успешный ответ сначала проверяется на JSON-совместимость: нечисловые времена, NaN, множества, циклы и другие невалидные данные не становятся валидными из-за удаления лишних полей. Поля верхнего уровня pipeline также не переносятся; его `video`, `video_id`, `elapsed_sec` не подменяют служебные данные runner. Это компактный артефакт для оценки, не архив evidence; идентификаторы и предсказания остаются закрытыми — не публикуйте `predictions.json`.

При ошибке возвращаются `video`, `status: failed`, `error` и `elapsed_sec`, без отрицательного вердикта. Отсутствующий файл имеет `error: MissingFile`, неоднозначный — `AmbiguousFile`. Для исключений хранится только имя класса (`NotImplementedError`, `ModuleNotFoundError`, `ValueError` и т. п.), без исходного текста и traceback. Неизвестный/невалидный ответ не считается `no_violation`.

Превышение жёсткого времени даёт `status: timed_out`, `error: TimeoutExpired`. Явные статусы pipeline `failed` / `timed_out` также сохраняются как отказы, но произвольный текст его ошибки и его вердикт удаляются. Для явно возвращённого `failed` используется обезличенный класс `RuntimeError`. Следующие записи всё равно обрабатываются.

После проверки target, бюджетов и локальных путей и создания `output_dir`, **до audit и запуска workers**, `output_dir/predictions.json` атомарно заменяется пустым списком текущего запуска. После каждой завершённой попытки файл атомарно заменяется всем накопленным префиксом, включая `MissingFile`, `AmbiguousFile`, ошибки подготовки запроса, отказы и таймауты workers. Запись идёт во временный файл на той же файловой системе, затем выполняется `os.replace`; старый файл не редактируется на месте. Прежние predictions не читаются и не используются повторно.

`KeyboardInterrupt` передаётся вызывающему коду: на диске остаётся последний опубликованный checkpoint завершённых попыток, а не запись о незавершённом видео. Ошибка audit до первого worker оставляет пустой snapshot. Ошибка публикации checkpoint возбуждает исключение и сохраняет предыдущий опубликованный snapshot; атомарная замена не гарантирует fsync/сохранность при отключении питания. Валидационная ошибка до инициализации snapshot не начинает новый запуск. Resume не реализован: новый вызов начинает с нуля; входной fingerprint для доказательства безопасного продолжения не ведётся.

Каждый вызов использует уникальную временную папку внутри `output_dir`; для каждого видео создаются отдельные request/response JSON. Штатный worker записывает только уже очищенный результат, не сырой ответ pipeline. После нормального завершения, обработанной ошибки или `KeyboardInterrupt` временная папка удаляется. Параллельные вызовы обязаны иметь разные `output_dir`: блокировки между ними нет, и общий `predictions.json` будет перезаписываться.

## Изоляция, время и ограничения

- Для каждого сопоставленного видео создаётся новый `sys.executable`; веса/состояние не разделяются между видео. Выбирайте интерпретатор с уже установленными локальными ML-зависимостями и локальными весами. Это намеренно учитывает холодный старт, но может быть медленнее повторного использования модели.
- Request содержит только путь к видео, имя target и мягкий бюджет: метки и истинный timestamp в worker не передаются. В командной строке дочернего процесса — только внутренний subcommand и пути к request/response, без паролей, токенов и медиа.
- `stdin`, `stdout`, `stderr` дочернего процесса направлены в `DEVNULL`, включая вывод native-библиотек. Между worker и родителем передаётся только очищенный JSON через локальный файл, без очередей/Pipe с кадрами или base64. Полный ответ pipeline и его проверка на JSON-совместимость могут временно занимать память worker, но runner не записывает сырой ответ/evidence. Собственные файловые записи доверенного pipeline этим не ограничены.
- До импорта pipeline окружение worker принудительно получает `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `HF_HUB_DISABLE_TELEMETRY=1`. `TMPDIR`, `TEMP`, `TMP` направлены в уникальную локальную временную папку запуска; окружение родителя не меняется.
- В worker установлен CPython audit hook: запрещены соединения, отправка UDP/sendmsg и DNS/name queries, включая прямой `_socket`. Создание socket, локальный `gethostname` и bind только на числовые IPv4/IPv6 loopback разрешены для инициализации Torch; wildcard/non-loopback bind запрещены. Даже соединение с локальным HTTP-inference endpoint недоступно: connect запрещён независимо от адреса. Это не запрет всех операций с socket и не ОС-песочница.
- При таймауте/прерывании Windows использует `taskkill /PID ... /T /F`, POSIX — отдельную сессию и `killpg(SIGKILL)`, затем гарантированно завершает/ожидает основной worker. Это устраняет обычных дочерних исполнителей вроде ffmpeg. Планирование ОС, запуск и очистка дерева имеют накладные расходы; фактический `elapsed_sec` может превысить `timeout_sec`, и это не скрывается.
- Это защита для доверенного локального кода, **не ОС-песочница** против вредоносного Python/native-кода. Native-сеть, специально отделённые процессы и враждебные filesystem-ссылки требуют изоляции/сетевого запрета на уровне ОС или физически отключённой сети. Если системное уничтожение дерева недоступно, основной worker всё равно завершается, но очистка всех потомков не гарантируется.
- Ошибки общей конфигурации и недоступный каталог результатов возбуждают исключение; возврат полного списка гарантируется для корректной конфигурации и доступного локального хранилища без прерывания. При аварийном выключении ОС/принудительном уничтожении родителя временные файлы могут остаться, но повторно не используются. Checkpoint содержит только последний опубликованный префикс, не подтверждение полного охвата labels.
- Не реализованный `ml.pipeline.analyze` даёт реальный отказ `NotImplementedError`; runner не подключает mock, не подставляет разметку и сам не создаёт метрики качества. Пример выше не утверждает работоспособность модели.

## Проверка

Из корня репозитория:

```text
.venv/Scripts/python.exe -m unittest tests.test_eval_runner -v
.venv/Scripts/python.exe -m ruff check ml/eval_runner.py tests/test_eval_runner.py
```

Тесты создают временные искусственные Python-модули под `artifacts/eval-runner-tests`, действительно запускают отдельные процессы, проверяют успех, отсутствие/неоднозначность файлов, исключения/импорт, таймаут и уничтожение потомка, offline-переменные, запрет сети, невалидные ответы и отсутствие утечки stdout. Синтетический ответ с 2 MB evidence проверяет allowlist, отсутствие сырых кадров в worker response, возвращённых записях и каталоге результатов. Регрессии прерывают второй worker и сравнивают точную первую завершённую запись на диске, проверяют checkpoint ошибок файлов/подготовки запроса и пустой snapshot при отказе audit до worker. Также проверяются канонические joins с сохранением исходных идентификаторов и отсутствие передачи разметки. Они не оценивают модель: никакие синтетические ответы не являются метриками на реальных видео. Установка зависимостей, загрузка весов и просмотр настоящих кадров не нужны.
