# Питч — 5 минут

Перед выступлением: проверить актуальность каждого утверждения. Слайды описывают целевую архитектуру отдельно от готового интерфейса. Говорить о подключённом ML и метриках только после подтверждения командой.

## 0:00–0:40 · Слайд 1. Задача

При проверке кассовой дисциплины недостаточно сказать, что в записи есть подозрительный эпизод. Проверяющему нужно понять, что именно видно, где находится событие и на каком основании его стоит проверить. Мы собираем этот путь в одном интерфейсе: от загрузки видео до конкретного эпизода с доказательствами. Сервис помогает специалисту принять решение. Он не заменяет его заключение.

## 0:40–1:20 · Слайд 2. Путь пользователя

Пользователь загружает MOV до 200 мегабайт. Интерфейс заранее проверяет расширение и размер и показывает передачу файла. Затем он опрашивает API и отображает этап обработки. Ошибка формата, неверный ключ, сбой сети или превышенное время ожидания получают понятное объяснение. После проверки появляется один из двух предусмотренных вердиктов и список найденных эпизодов.

## 1:20–2:25 · Слайд 3. Демо

[Показать загрузку заранее подготовленной записи. Если API не подключён, прямо сказать: «Сейчас демонстрируем интерфейс на фикстуре; это не анализ этого видео».]

В результате исходная запись остаётся рядом с карточками. По таймкоду или метке на шкале можно перейти к моменту события. В карточке есть тип, описание наблюдаемых действий и до трёх кадров. Каждый кадр увеличивается для проверки деталей. Нормативное основание показывается отдельно: документ, пункт, точная цитата и ссылка. Если основание отсутствует в ответе, интерфейс сообщает об этом, а не подставляет вымышленную норму.

## 2:25–3:20 · Слайд 4. Технический подход

Целевая схема решения разделяет интерфейс, API и локальный анализ. React-интерфейс отправляет файл в FastAPI и получает идентификатор задания. На стороне команды предусмотрены очередь, анализ видеокадров, детекция и временные правила, затем локальная VLM-проверка кандидатов и сборка результата. Интернет не должен требоваться после загрузки моделей. Факт готовности и офлайн-работу этой части подтверждает команда отдельным прогоном; фронтенд сам по себе этого не доказывает.

## 3:20–4:10 · Слайд 5. Проверка качества

По плану качество оценивается не только по общему вердикту. Нужны полнота по нарушениям, ложные срабатывания, точность таймкода, классификация и время обработки. Отдельная проверка на другом ракурсе показывает, насколько решение зависит от расположения камеры. Цели команды — обработка видео не более чем за пять минут и устойчивость при нескольких одновременных загрузках. Здесь перед выступлением нужно показать только реальные результаты отчёта Нурхана, не подменяя их целями.

## 4:10–5:00 · Слайд 6. Границы и ценность

Камера не позволяет доказать действия в банковской системе или намерения человека. Поэтому описание ограничивается наблюдаемым. Предусмотрен отказ от распознавания лиц и звука. Важные ограничения — новый ракурс, перекрытия и несовместимые кодеки — требуют отдельной проверки. Главная ценность интерфейса в том, что проверяющий получает связную цепочку: эпизод, момент видео, визуальное доказательство и подтверждённое основание. Это и есть результат, который мы показываем в демо.
