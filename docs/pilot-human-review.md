# Ручная проверка восьми пилотных видео

Алпамыс делает первичную ручную разметку; Олжас независимо проверяет положительные решения, неясные и спорные случаи. Цель — передать проверяемые человеческие решения с происхождением, временем и явно сохранёнными разногласиями. Это отдельная работа с development-видео; она не заменяет новую съёмку под другим ракурсом, evaluator или проверку качества модели.

`pending`, `unclear` и другие статусы ручной проверки относятся к локальному sidecar. Контракт API К1 сохраняет два вердикта; этот инструмент его не меняет.

Конкретные восемь ID и разметка Алпамыса пока не переданы. Инструмент и эта инструкция не выбирают их самостоятельно. До получения согласованного списка нельзя заполнять реальные записи предположениями или объявлять пилот готовым.

## Локальные файлы

- `data/pilot-review/inventory.json` — согласованный список клипов, фактические SHA256 содержимого, техническая длительность и известные сведения о ракурсе / группе источника.
- `data/pilot-review/adjudication.json` — первичные и независимые человеческие решения, покрытие просмотра, эпизоды, разногласия и согласование дублей.

Оба файла остаются под игнорируемым `data/`. Видео, кадры, частные описания и заполненные решения не добавляются в Git и не отправляются облачным инструментам. Исходные organiser labels сохраняются; спорное уточнение записывается отдельно со ссылкой на происхождение, а не переписывает исходную метку.

Используйте существующее окружение разработки проекта; новые Python-зависимости для этого инструмента не добавляются. Для технических метаданных нужен `ffprobe` из PATH; путь можно переопределить через `--ffprobe`. Синтетические тесты используют существующий pytest. Модели, новый UI, evaluator и экспорт в другие форматы для этой работы не требуются.

## Команды

Команды ниже — инструкция для запуска после получения согласованных восьми ID; они не означают, что реальные входы уже получены или проверены.

```sh
python tools/pilot_review.py init \
  --pilot-ids /absolute/path/approved-pilot-ids.json \
  --videos-dir /absolute/path/videos \
  --labels /absolute/path/labels.xlsx
python tools/pilot_review.py validate
python tools/pilot_review.py summary
python tools/pilot_review.py validate --require-complete
```

`--pilot-ids` принимает JSON-массив ровно восьми согласованных ID либо объект с `pilots`: списком записей `video`, необязательным `relative_path` относительно `--videos-dir`, а также `angle_id` и `source_group` со значением `null`, если они неизвестны. Это входной список, явно одобренный человеком; инструмент не выбирает восемь ID по меткам, именам или содержимому. Пустой список — только незавершённый черновик, а не допустимый запуск `init`.

`init` вычисляет фактические хеши и технически проверяет только выбранные восемь файлов. Он сохраняет происхождение исходного XLSX: SHA256 и исходные значения ячеек меток. Ручные решения, имена reviewer, даты и события создаются пустыми / незавершёнными. При повторном запуске существующая пара файлов сначала проверяется; заполненная разметка сохраняется, а не перезаписывается.

Обычный `validate` допускает структурно корректный незавершённый черновик. `--require-complete` требует именно диагностический `review_handoff_ready`; это не проверка `full_truth_ready`. `summary` отдельно показывает оба признака готовности. Проверки сверяют фактические хеши восьми файлов и сохранённое происхождение источников; изменение исходника требует явного разбора, а не незаметного обновления подписанной записи.

## Порядок ручной работы

1. Получить от Алпамыса согласованный список восьми ID, локальные пути и его первичную разметку. Проверить соответствие ID файлам. Хеши вычислять по фактическим локальным файлам; длительность брать из технического probe, а не из имени или предполагаемой частоты кадров.
2. Для каждого клипа указать реальное покрытие первичного просмотра: `primary_only` — размечено только первичное событие; `full_clip` — просмотрен весь клип. Отсутствие других записей при `primary_only` не означает отсутствия других событий.
3. Для каждого эпизода записать наблюдаемое действие, участника по роли без идентификации личности, предмет, начало, решающий момент, конец и видимость. Времена относятся к текущему клипу: `0 ≤ начало ≤ решающий момент ≤ конец ≤ длительность`. Если шаг не виден, допускается «неясно»; пропущенный в кадрах шаг не доказывает отсутствия проверки.
4. Олжас выполняет отдельную ручную проверку положительных решений, неясных и спорных случаев. Второй reviewer должен отличаться от первого. Имя и дата в формате `ГГГГ-ММ-ДД` отражают реально выполненную проверку: инструмент не подписывает записи и не подставляет дату вместо человека.
5. Неразрешённые разногласия людей перечислить в `disagreements`, включая причину и текущее решение; они блокируют `full_truth_ready`. Если человеческий вывод отличается от organiser label, сохранить пояснение отдельно в `organizer_clarification`: `reference: inventory.organizer`, исходный `source_sha256` и непустой `note`; исходную метку не исправлять. После двух согласованных независимых человеческих проверок такое уточнение само по себе не блокирует `full_truth_ready`. Сохранить возможность согласованного «неясно»; не заменять его отрицательной меткой и не разрешать спор по confidence модели или наличию правовой ссылки.
6. Для одинакового содержимого согласовать решение на уровне группы точных дублей. Одинаковый SHA256 означает одинаковое содержимое, а не независимую съёмку. Группа дублей не является `camera_id`, `angle_id` или доказательством нового ракурса.
7. Если реальные `angle_id` и `source_group` выяснились после `init`, записать их в `adjudication.clips[].reviewed_context`, а не менять исходный inventory или список выбора. Указать `kind: human`, реальных `reviewer` / `date` и `source_reference`. Если контекст неизвестен, оставить его неизвестным. Это допустимо для development-пилота и не даёт основания объявлять строгий camera / angle holdout.

Отрицательное решение о всём клипе допустимо только после `full_clip`. Отклонение одного эпизода не является отрицательным решением о всём клипе. Автоматически созданный пустой черновик, технически валидный JSON и отсутствие найденных событий отрицательной меткой не являются. Если исходное время evidence не подтверждено явными source metadata, оставить его неизвестным; не угадывать его по confidence или имени файла.

`inventory.json` хранит неизменяемый исходный снимок. Для нового подтверждённого контекста редактируется только adjudication; при наличии `reviewed_context` используются его явно заданные `angle_id` и `source_group`, иначе — значения inventory. Не пересчитывать вручную связывающий хеш и не запускать заново выбор восьми ради новой информации: это нарушит происхождение либо потеряет связь с уже выполненными проверками. `summary` показывает лишь числовые счётчики контекста; подробности остаются в локальном JSON.

На уровне клипа `coverage` принимает `pending` / `primary_only` / `full_clip`, а `clip_decision` — `pending` / `has_confirmed_event` / `no_violation` / `unclear`. Подписи просмотра находятся в `primary_review` / `secondary_review`, явные разногласия — в `disagreements`. Для группы точных дублей заполняются `duplicate_decisions`, включая согласованное решение, двух разных человеческих reviewer, пояснение и ссылки на все её события по `video_key` / `event_id`.

В [схеме](../tools/pilot_review_schema.py) заданы поля и enum. Для роли используются `cashier` / `client` / `collector` / `other` / `unknown`, для видимости — `clear` / `partial` / `unclear`. `type_id` — текущий runtime ID каталога либо `null`, если тип ещё не установлен. Фрагмент полей незавершённого эпизода ниже не является полным входным файлом и не добавляется автоматически:

```json
{
  "type_id": null,
  "actor_role": "unknown",
  "visibility": "unclear",
  "t_start": null,
  "t_peak": null,
  "t_end": null,
  "consensus": "pending"
}
```

У полной записи эпизода есть уникальный UUID `event_id`, скопированные из inventory `video_key` / `content_sha256`, непустые `action` и `object` (допустимо явное `unknown`). В `primary` / `secondary` человек записывает `kind: human`, свои `reviewer` / `date` и решение `confirmed` / `rejected` / `unclear`. Итоговый `consensus` допускает также `pending` и `disputed`; спор сопровождается явным описанием разногласия. Эти поля заполняются по выполненной работе, а не копируются из примера как подтверждение.

## Три уровня готовности

| Уровень | Что требуется | Что можно передать |
| --- | --- | --- |
| Структурно корректный черновик | Правильная структура, допустимые enum и корректные заданные времена. Незавершённые ручные записи допустимы. | Черновик для продолжения работы; готовность ручной проверки не заявляется. |
| `review_handoff_ready` | Все восемь имеют первичную человеческую проверку и явно указанное покрытие `primary_only` / `full_clip`. Положительные, неясные и спорные случаи проверены вторым, отличающимся человеком. Разногласия перечислены; решения для точных дублей согласованы, в том числе допустимо согласованное «неясно». | Диагностическую передачу результатов ручной проверки с сохранёнными ограничениями. |
| `full_truth_ready` | Все восемь полностью просмотрены (`full_clip`), решения согласованы, неясных случаев и нерешённых разногласий нет; видимость событий — `clear`, все необходимые времена заданы. Отрицательные решения относятся только к полностью просмотренным клипам. | Полную согласованную разметку в пределах этого пилота. |

Неизвестные ракурс и группа источника сами по себе не блокируют development-передачу. `primary_only` и «неясно» могут быть совместимы с диагностической передачей, но не с `full_truth_ready`.

Валидатор проверяет структуру, enum, времена и записанные условия готовности. Он не доказывает, что человек действительно просмотрел видео, что два reviewer фактически независимы или что их решение истинно. Эти факты подтверждаются самой ручной работой и её происхождением.
